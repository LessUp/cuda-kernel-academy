# 开发流程

CUDA Kernel Academy 遵循单一、轻量的工作流程，旨在**交付聚焦的修复，避免流程漂移**。

## 原则

- **OpenSpec 优先**：非琐碎工作使用 OpenSpec
- **短生命周期分支**
- **合并前评审**
- **最小仪式**
- **无并行规格系统**
- **当仓库范围的收尾程序处于活跃状态时，除非子域真正独立，否则将其保留在一个 umbrella change 中**

## 标准循环

### 1. 判断工作是否需要规格

当变更具有以下特征时使用 OpenSpec：

- 架构性
- 跨模块
- 开始时模糊不清
- 足够大，以至于实现不应仅依赖聊天记录

对于微小的拼写修正或明显的单文件修正，完整的 proposal 是可选的。

### 2. 创建或刷新 OpenSpec 变更

预期结构：

```text
openspec/
├── changes/
│   └── <change-name>/
│       ├── proposal.md
│       ├── specs/spec.md
│       ├── design.md
│       └── tasks.md
└── changes/archive/
    └── YYYY-MM-DD-<change-name>/
```

保持各文件诚实对齐：

- `proposal.md` = 为什么存在这个变更
- `specs/spec.md` = 需求和场景
- `design.md` = 决策和权衡
- `tasks.md` = 可操作的实现清单

### 3. 从任务清单实现

保持实现分支狭窄。如果工作实质性地扩展了，更新 spec 而不是让代码偏离原始意图。

### 4. 仅验证重要内容

典型检查：

```bash
pre-commit run --all-files
npm ci
npm run docs:build
cmake --list-presets
```

GPU 相关的变更必须在真实 CUDA 机器上验证。

### 5. 合并前评审

对非琐碎变更使用 `/review`。评审是标准循环的一部分，不是可选的额外步骤。

推荐评审点：

- 需求覆盖度
- 正确性和风险
- 工作流/文档一致性
- 不必要的复杂性

### 6. 及时合并

避免以下之间的长期分歧：

- 本地分支
- 云端代理分支
- 生成代码分支
- 延迟评审分支

本仓库倾向于快速收敛，而非堆积流程开销。

### 7. 归档已完成的工作

归档到：

`openspec/changes/archive/YYYY-MM-DD-<change-name>/`

不要在 `openspec/changes/` 中留下“已完成”的工作。

## 工具指导

### `/review`

在以下情况合并前使用：

- 多文件变更
- 工作流/配置变更
- 重新定义贡献者行为的文档
- 任何架构性内容

### `/research`

仅用于仓库真正依赖的外部事实或最新工具文档。

### `/remote`

用于隔离的后台执行或有限的研究任务。不要将其作为日常开发的默认模式。

### `/fleet`

谨慎使用。本仓库倾向于更少、更长时间、更专注的会话，以减少配额消耗并避免并行漂移。

## 收尾偏向

当不确定时，选择以下选项：

- 减少维护负担
- 移除陈旧或低信号内容
- 保持公共表面精致
- 使未来的最终 bug 修复更容易落地
